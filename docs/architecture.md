# アーキテクチャ設計（architecture.md）

このドキュメントは **「どう作るか」**（技術構成・データの流れ・データ設計・非機能）をまとめたものです。
「何を作るか」は [`requirements.md`](requirements.md) を参照。

---

## 1. 技術スタック

| 領域 | 技術 | 役割 |
|---|---|---|
| アプリ枠 | Tauri v2 | 1つのコードで Mac / Windows / Linux（将来モバイル）へ展開。 |
| UI | TypeScript + React + Vite | 画面。型で書き間違いを早期に検知。 |
| 中核ロジック | Rust | データ処理や堅牢さが要る計算。 |
| データ | SQLite（`rusqlite`） | 端末内で完結する1ファイルDB。 |

> 🔒 機密データを扱うアプリでは、`rusqlite` の `bundled-sqlcipher` 機能に切り替えると
> DBファイルごと暗号化できます（このテンプレートでは無効）。

## 2. データの流れ（レイヤー構成）

画面は直接SQLを書かず、必ず Rust のコマンド層を通してデータを扱う。

```
[React 画面]  --- invoke("list_items") --->  [Rust コマンド (lib.rs)]
     ^                                              |
     |                                              v
     +------------ JSON で結果を受け取る -------  [DB層 (db.rs)]  <-->  [SQLite]
```

- **画面（`src/screens/*.tsx`）**：`@tauri-apps/api` の `invoke()` でコマンドを呼ぶだけ。
- **コマンド層（`src-tauri/src/lib.rs`）**：`#[tauri::command]` で公開。状態（DB接続）を受け取り、DB層へ委譲。
- **DB層（`src-tauri/src/db.rs`）**：接続・マイグレーション・初期データ・読み書きを担当。SQLはここに集約する。

この分離により、「画面はデータの出し方を知らない／DBは画面を知らない」状態を保てる（変更に強い）。

## 3. データ設計

このテンプレートには、動作確認用の汎用テーブルを1つだけ用意している。
自分のアプリでは、この `items` を必要なテーブルに置き換えていく。

### items（サンプル）
| 列 | 型 | 説明 |
|---|---|---|
| id | INTEGER | 主キー |
| title | TEXT | タイトル |
| note | TEXT | メモ（任意） |
| category | TEXT | 分類ラベル |
| is_active | INTEGER | 有効フラグ（0/1） |
| sort_order | INTEGER | 表示順 |
| created_at | TEXT | 作成日時 |

### マイグレーションの考え方
SQLite の `user_version` を使い、未適用の差分だけを順に実行する（`db.rs` の `run_migrations`）。
テーブルを増やすときは `SCHEMA_V2` を書き、`version < 2` の分岐を追加する。
こうすると、**既存ユーザーのDBを壊さずに**構造を更新できる。

## 4. UI設計（アプリシェル）

- **サイドバー**：ナビ項目＋新規作成ボタン＋アカウント欄。
- **レスポンシブ3段階**：
  - 広い（≥1024px）＝全開サイドバー
  - 中間（640〜1023px）＝アイコンだけのレール（クリックで一時展開）
  - モバイル（<640px）＝ドロワー（ハンバーガー＋暗幕）
- **テーマ**：ライト/ダークをトークンで両対応。OS設定（`prefers-color-scheme`）と手動切替（`data-theme`）の両方に追従。
- 詳細な色・余白のルールは [`design.md`](design.md) を参照。

---

## 5. 非機能（テンプレートの前提）

| 分類 | 方針 |
|---|---|
| オフライン | ネット接続なしで動作。データは端末内に保持。 |
| データ保全 | DBは `app_data_dir`（OSごとのアプリ専用領域）に保存。 |
| 移植性 | Mac / Windows / Linux で同一動作。将来モバイルへ展開可能。 |
| 拡張性 | コマンド層・DB層を足していくだけで機能追加できる構成。 |
